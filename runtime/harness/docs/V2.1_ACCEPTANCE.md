## Freeze rules

From this point the harness enters a **stable-use period**. Unless a real project exposes a
definite bug, do NOT:

- refactor the harness
- add abstraction layers
- add a database
- add a UI
- introduce dependencies
- modify the ChatGPT adapter
- modify the Worker protocol
- extend the Router

Real-project problems are solved first in **Project config / Workspace config / Task
definition** — not by editing the harness.

### If the harness must change

Classify the cause first:

| Class | Cause | Fix here first |
| --- | --- | --- |
| **A** | Project config (e.g. wrong workspace `paths`) | `PROJECT.yaml` / `workspaces.json` |
| **B** | Task definition (e.g. vague `success_criteria`) | the task record |
| **C** | Worker prompt | packet / template |
| **D** | Genuine harness bug | harness core — **only if A/B/C cannot explain it** |

After any **D** change, all four suites must be re-run:

```
node acceptance.js     # V1: 59
node yamltest.js       # YAML: 33
node v2e2e.js          # V2: 60
node cli.js verify     # protected worker: 10 gates
```

Generality must never be broken to satisfy one project.

## Step 1 - read-only reconnaissance

Given a project name and path, inspect **without modifying anything**:

1. project root and whether it is a real boundary
2. project type
3. main file structure
4. existing Git (branch, status, uncommitted changes)
5. existing README / docs / status records
6. credentials or sensitive files (must never be committed)
7. generated directories or caches (must be ignored)
8. which areas could form Workspaces

**No real file is modified during reconnaissance.**

---

## Step 2 - Workspace design

For the first real project, propose **2-4 workspaces**, not more.

Split only when one of these holds:

- context is durably different
- a different Worker role is needed
- file-access boundaries clearly differ
- work advances independently over time
- mixing them would cause context pollution

**Do not** use "one directory = one workspace" or "one file type = one workspace". A
Workspace is a **context boundary**, not a folder classifier.

### Report before doing anything

- **Project**: suggested `project_id`, name, path, type
- **Suggested Workspaces**: for each — `workspace_id`, name, `type`, `paths`,
  `default_worker_role`, and *why it deserves to be separate*
- **Not split out**: which areas stay together, and why
- **Git**: current state, whether to init, proposed `.gitignore`
- **Risks**: only genuine ones

**Wait for approval of the Workspace design.**

---

## Step 3 - register (after approval)

1. register the Project
2. scaffold `.ai`
3. create the workspaces
4. create the task registry
5. inspect the generated result
6. **never overwrite existing project files**
7. **never modify business code**

Then generate `PROJECT_STATE.md`, `DECISIONS.md`, `PROJECT_TASKS.md` and per-workspace
`WORKSPACE_STATE.md` / `TASKS.md`.

**These must be built from the real project content.** Copying harness development history
into them is forbidden.

---

## Step 4 - Git baseline

If the project already has Git: **do not re-init**. Record `branch`, `git status`, and any
pre-existing uncommitted changes. **Protect the user's uncommitted work.**

If it has no Git: check the project boundary and `.gitignore` first, then initialise only
once safe.

The baseline commit must happen **before any AI business change**.

If the project holds large binary assets, judge whether Git LFS is needed. **When unsure, do
not auto-commit large files.**

---

## Step 5 - first real Worker

Do **not** reuse the harness test conversation. Create a **brand-new** ChatGPT conversation
for the first real workspace, bound to `project_id` + `workspace_id` + `role`.

First message is the initialization packet, carrying only:

- project minimum context
- current Workspace state
- Workspace rules
- a real file overview
- the necessary global Decisions

Not the entire project.

---

## Step 6 - initialization acceptance

The Worker is asked only to **understand**, and to reply with:

1. the Project goal as it understands it
2. the Workspace's responsibility as it understands it
3. the Workspace's key files
4. known constraints
5. the most worthwhile current Task
6. what it has **not** been shown, and therefore must not assume

DeepSeek Review: **PASS / RETRY / BLOCKED**. Initialization allows **at most 1 RETRY**.

---

## Step 7 - first real Task

Must be: real, clearly bounded, low risk, few files, with explicit `success_criteria`, and
verifiable.

Prefer: a small bug, a small code review, one clear copy change, one local logic problem, a
state-tidying task.

Avoid: large refactors, architecture rewrites, mass deletion, cross-workspace major changes,
release processes, or touching dozens of files at once.

---

## Step 8 - the full closed loop

```
Task READY
  -> DeepSeek reads Project State / Workspace State / Task / real files
  -> build the hierarchical packet
  -> send to the ChatGPT Worker
  -> wait_complete
  -> read_reply
  -> DeepSeek Review (PASS / RETRY / BLOCKED; RETRY max 3)
  -> only after PASS may files change
  -> edit files
  -> inspect git diff
  -> run available verification (build / tests / lint / static check / explicit human criterion)
  -> DeepSeek reviews the result
  -> success_criteria satisfied
  -> Task DONE
  -> sync WORKSPACE_STATE.md, workspace TASKS.md, PROJECT_STATE.md summary, tasks.json
  -> update DECISIONS.md only if a durable decision was made
```

---

## Step 9 - what to watch for

This acceptance is **not** mainly about whether the task got done. Record whether the harness
showed any of:

1. packet context too large
2. packet context insufficient
3. wrong workspace selected
4. wrong router decision
5. worker read the wrong conversation
6. worker round drift
7. `wait_complete` misjudgement
8. `read_reply` losing structure
9. unreasonable RETRY
10. DeepSeek Review passing too early
11. worker editing beyond the task boundary
12. state files out of sync with real code
13. unrelated changes in `git diff`
14. cross-workspace information genuinely needed but unavailable
15. the workspace split itself proving wrong

These are **real data**. Only after something actually occurs is a harness change considered.
