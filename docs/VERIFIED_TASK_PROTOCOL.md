# The Verified Task Protocol

A hand-off between two different AI providers is only verifiable if the hand-off itself is
data. This document describes the contract that makes that true in this repository: what a
task carries, how a reply is proven to belong to the task that asked for it, and what the
code does when that proof is missing.

It is written for a developer who wants to know why the protocol exists before reading the
code. Every claim below is taken from the shipped source in `workbench/protocol/`,
`workbench/seats/` and `workbench/transports/`; the function and field names are the real
ones.

## 1. What problem this solves

An agent that answers is not the same thing as an agent that answered *this*. Without a
protocol, four specific failures are not detectable by the receiver, because in each case the
reply looks like a perfectly good answer.

### Stale reply

The worker answers an *older* dispatch, and the answer arrives late. Without the protocol the
reader sees a well-formed reply that discusses the right files and reports success, and has no
field to compare it against: prose does not carry the identity of the request it belongs to.
The code names the general case `STALE_OR_UNCORRELATED_REPLY`, and it is a terminal
`RUN_STATUS`, not a warning.

### The wrong conversation

The reply comes from a worker session that was never dispatched to. In this repository that is
a live risk rather than a theoretical one: the browser transport reads assistant turns out of
a page that can lag minutes behind the conversation, and it has a documented index fallback
that reads the *newest* assistant turn when the recorded index is unavailable. Nothing in the
text itself says who it was written for. The whole defence is that the reply must carry
`RUN_ID_ACK` equal to the run that was dispatched, so a correct-looking answer from the wrong
session is refused rather than merged.

### A duplicate send

The same instruction is delivered twice, so the worker either does one task twice or does two
tasks. This is the failure the delivery state machine is shaped around: the transport is
forbidden to wait for an answer and forbidden to retry a packet that may already have landed,
the single legal action while a run is pending is `observe`, and `SEND_UNCERTAIN` - the state
that says "we cannot say whether it landed" - has no outgoing transitions at all. See
section 8.

### The source changing after review

The worker reasoned about revision A, and by the time a human reviews or approves, the file on
disk is revision B. The review is then about nothing. Source hashes are captured at dispatch,
acknowledged by the worker, and re-verified before review, and a mismatch ends the run as
`SOURCE_CHANGED_SINCE_REVIEW` regardless of how good the answer looks. See section 6.

### A note on the code's own list

The header comment in `workbench/protocol/protocol.js` names its own four failure modes: stale
reply, wrong conversation, duplicate send, and *reconnect ambiguity* (after a restart, nobody
can say whether a dispatch committed). Reconnect ambiguity is answered by the same mechanism as
the other three - the `run_id` field echoed back as `RUN_ID_ACK` - and by `SEND_UNCERTAIN`
being terminal, so an uncertain send is a fact to be resolved by a human rather than a state a
program may retry out of.

The four modes above are all represented in shipped code: `RUN_STATUS.STALE_OR_UNCORRELATED_REPLY`,
`RUN_STATUS.SOURCE_CHANGED_SINCE_REVIEW`, `RUN_STATUS.SEND_UNCERTAIN`, and the correlation
dispositions in section 4.

## 2. The envelope

The envelope is built by `buildEnvelope(spec)` and checked by `validateEnvelope(env)` in
`workbench/protocol/protocol.js`. A packet is *rendered* from the envelope by
`workbench/protocol/renderers.js`; the envelope is the protocol and the packet is prose, and
conflating them is the mistake the renderer layer exists to prevent.

`buildEnvelope` returns `{ok: false, error: 'envelope is missing required field(s): ...'}` when
any of `taskId`, `projectId`, `workspaceId` or `seatId` is absent. The `run_id` is generated by
`newRunId(taskId)` unless the caller supplies one, and is shaped
`RUN-<stamp>-<tag>-<rand>`.

| Field | What it is for | What breaks without it |
| --- | --- | --- |
| `protocol_version` | The protocol revision, currently the constant `PROTOCOL_VERSION` = `0.2.0`. | A record cannot be interpreted later, and `validateEnvelope` cannot tell an old envelope from a malformed one. |
| `run_id` | The identity of this one dispatch. Generated by `newRunId(scope)`, or supplied by the caller. | Nothing can be correlated. This is the field the reply echoes as `RUN_ID_ACK`. |
| `task_id` | Which task in the project this run is. | A run cannot be attributed to the work it was created for, and two turns of one goal become indistinguishable. |
| `project_id` | The project the run belongs to. | The seat ownership guard cannot compare the envelope against the seat, and evidence records cannot be scoped. |
| `workspace_id` | The workspace inside the project. | Same as above, at a finer grain: two workspaces of one project could be confused. |
| `seat_id` | The seat the run is dispatched to. | `seat.dispatch` refuses an envelope whose `seat_id` does not match the seat, so a missing value makes dispatch impossible; with the check weakened, a run could be handed to a seat that never agreed to it. |
| `task.title`, `task.description` | Human-facing naming of the work. Rendered into the packet. | The worker gets an unattributed instruction and the record has no readable label. |
| `source_files[]` | The identity of what the worker is asked to reason about. Each entry is `{path, sha256, bytes, present_at_dispatch}` from `captureSourceFiles(projectRoot, relPaths)`; `path` has backslashes normalised to `/`. | TOCTOU has nothing to compare against, and the worker has no statement of which revision it was given. |
| (derived) source set hash | Not stored on the envelope: computed on demand by `hashSourceSet(files)`. For a single file it is that file's own `sha256`, verbatim; for several it is the sha256 of the sorted, newline-joined content hashes, so it is order-independent. | The worker's `SOURCE_HASH_ACK` could only be a metadata hash, and a correct single-file run would look mismatched. |
| `permissions.read_scope` | What the run may read. | The worker's scope becomes aspirational prose; a reviewer cannot tell whether reading something was permitted. |
| `permissions.write_scope` | What the run may write. | A run that writes cannot be judged against a declared limit, and `diffScopeOk` in the evidence record has no baseline. |
| `permissions.deny` | Explicit prohibitions. | A prohibition nobody recorded cannot be enforced or audited. |
| `permissions.approval_required` | Paths or actions that need human approval before a write. | An approval gate becomes an after-the-fact opinion. |
| `success_criteria[]` | The criteria the review is conducted against. Rendered by `criteriaBlock`. | `reviewPrompt` reviews against an empty list, and any answer becomes unfalsifiable. |
| `expected_output` | What a usable answer looks like. | The reviewer has no stated target, so a vague reply passes by default. |
| `review_requirements.required` | Whether a review is required at all. In `buildEnvelope` this is `reviewRequirements.required !== false`, so the default is `true`. | The record cannot distinguish "not reviewed yet" from "review not needed". |
| `review_requirements.independent_provider` | Whether the review must come from a provider other than the worker's. Only `=== true` sets it. | The cross-vendor constraint would be assumed rather than declared, and `checkIndependence` would have nothing to check. |
| `review_requirements.min_reviewers` | A recorded minimum, defaulting to `1` when absent or non-finite. | Recorded intent is lost. Note that `checkIndependence` does not read this field, so it is not enforced by the current code. |
| `review_requirements.note` | Free text explaining the requirement. | Context for a human reading the record is lost. |
| `request` | The instruction itself, rendered into the packet under `[REQUEST]`. | The worker is asked to act without being told what to do. |
| `created_at` | When the envelope was built. | The record has no start time and a stale envelope cannot be identified as such. |

### What `validateEnvelope` actually checks

It is deliberately shallow, and says so: it checks that required fields exist and have the
right type, not that the values are sensible.

- `protocol_version`, `run_id`, `task_id`, `project_id`, `workspace_id`, `seat_id`,
  `created_at` must each be a non-empty string.
- `protocol_version` must equal `PROTOCOL_VERSION`.
- `source_files` must be an array; every entry needs a non-empty string `path`, and the field
  `sha256` must be **present** - `null` is allowed, absence is not.
- `permissions` must be an object whose `read_scope`, `write_scope`, `deny` and
  `approval_required` are arrays.
- `success_criteria` must be an array, and `review_requirements` must be an object.

`seat.dispatch` calls `validateEnvelope` before rendering and refuses an invalid envelope with
`envelope is invalid: ...`.

## 3. The acknowledgement block

The ack block is the correlation mechanism. It is emitted by `ackBlock(envelope)` in
`workbench/protocol/renderers.js` and must appear in every rendered packet, whatever the
dialect: the two renderers in `RENDERERS`, `structured` (`renderStructured`) and `human`
(`renderForHuman`), both emit it, and the regression suite asserts it. The two labels are the
module constants `ACK_RUN` = `RUN_ID_ACK` and `ACK_SOURCE` = `SOURCE_HASH_ACK`.

The block instructs the worker to begin its reply with these two lines before anything else:

```
RUN_ID_ACK: <envelope.run_id>
SOURCE_HASH_ACK: <source set hash>
```

where the source set hash is `hashSourceSet` over the bound files, or the literal string
`NO_SOURCE_BOUND` when no file with a non-null `sha256` was bound. The block also states that a
worker which cannot read a source file must write `SOURCE_HASH_ACK: UNREADABLE` rather than
invent a value, and that a mismatch means the reply cannot be attributed to the task at all.

`parseAck(replyText)` pulls the values out of the reply. Two details matter:

- The *label* is matched case-insensitively, because the pattern is built with the `i` flag.
- The *value* is captured as a run of characters that are not whitespace, not a backtick, not a
  single quote and not a double quote, so trailing punctuation and prose are not swallowed.
  `source_hash_ack_raw` additionally captures the rest of the `SOURCE_HASH_ACK` line.

### Comparison is exact byte equality

The comparison is done with the strict inequality operator, with no normalisation whatsoever.
A reply whose ack is not byte-identical to the expected value is quarantined. The source
comment states that an earlier revision forgave letter case, that this was a mistake, and that
it has been removed - a run id is an opaque handle, and any tolerance added to make a
mismatching reply correlate is indistinguishable from inventing a correlation.

The following are therefore not permitted, and are not implemented anywhere in this
repository:

- **No case-insensitive matching.** `RUN-ABC` and `run-abc` are different acks. The regression
  suite rejects a case-different run id explicitly.
- **No substring or prefix matching.** The comparison is `!==` on the whole value, so an ack
  that contains the run id plus anything else does not pass.
- **No "latest reply" guessing.** No code path accepts the newest available reply without a
  matching ack. Where a transport reads the newest assistant turn as a fallback, the file
  states plainly that the caller checks `run_id_ack` and that the protocol, not the index, is
  what guarantees the right answer.
- **No proceeding when the ack is missing.** A missing `RUN_ID_ACK` produces the disposition
  `MISSING_ACK`, which is a refusal, never implicit agreement.

The source hash ack is required only when the envelope bound at least one file whose `sha256`
is non-null. A run with no bound source legitimately has nothing to ack, and the code skips
that check rather than demanding an empty value.

## 4. Correlation outcomes

Two functions perform correlation, and they report different vocabularies. Both are in
`workbench/protocol/protocol.js`.

### `checkCorrelation(envelope, replyText, opts)`

Returns `{ok, status, disposition, detail, ack}` plus `expected` on mismatch.

| `disposition` | `status` | Produced when |
| --- | --- | --- |
| `CORRELATED` | `null` | `run_id_ack` equals the expected run id, and the source ack matches when source was bound. |
| `MISSING_ACK` | `STALE_OR_UNCORRELATED_REPLY` | The reply carries no `RUN_ID_ACK`. |
| `RUN_ID_MISMATCH` | `STALE_OR_UNCORRELATED_REPLY` | The reply acks a different run id. |
| `MISSING_SOURCE_ACK` | `STALE_OR_UNCORRELATED_REPLY` | The run bound source files and the reply carries no `SOURCE_HASH_ACK`. |
| `SOURCE_ACK_MISMATCH` | `SOURCE_CHANGED_SINCE_REVIEW` | The source ack is not the source set hash dispatched. |

The expected run id is `opts.expectedRunId` when supplied, otherwise `envelope.run_id`. The
expected source hash is `opts.expectedSourceHash`, otherwise `hashSourceSet` over the bound
files. Passing an immutable snapshot through `opts` is the documented expectation; the caller
that does not do so is reading a value that can move, which is exactly what section 5 is about.

### `correlateWithSnapshot(envelope, snapshot, replyText, opts)`

Returns `{ok, disposition, mismatched_fields, trace, ack, status, detail}`.

| `disposition` | `status` | Produced when |
| --- | --- | --- |
| `CORRELATED` | `null` | Every checked field matches `mismatched_fields` is empty. |
| `CORRELATION_MISMATCH` | `SOURCE_CHANGED_SINCE_REVIEW` if any mismatched token starts with `source_hash`, otherwise `STALE_OR_UNCORRELATED_REPLY` | One or more fields failed. |

`mismatched_fields` holds field-level tokens rather than prose, so a failure names the field
that failed: `run_id_ack:MISSING`, `run_id`, `thread_id`, `turn_id`,
`source_hash_ack:MISSING`, `source_hash_ack`. Thread and turn ids are checked only when the
snapshot recorded them *and* the transport reported them; the source check is skipped when
nothing was bound.

Note that this function has no `MISSING_ACK` label of its own: an absent ack appears as the
token `run_id_ack:MISSING` inside `mismatched_fields`. The two vocabularies are as described
here.

### The rule

An uncorrelated reply is discarded and never passed to review. In
`workbench/protocol/runs.js`, `completeFromReply` correlates first; when `corr.ok` is false it
sets `run.status` to the correlation status, logs `run.uncorrelated`, and returns
`ok: false` with the note:

> The reply was NOT passed to review. A reply that cannot be attributed is not a result.

The run statuses that can be reached this way are the terminal values in `RUN_STATUS`, which
is otherwise `DISPATCHED`, `SEND_PENDING`, `ASSISTANT_PENDING`, `AWAITING_REVIEW`, `COMPLETE`
and `BLOCKED`.

## 5. The frozen snapshot

`workbench/protocol/correlation.js` exists because persisted records were correct while the
live path reported `RUN_ID_MISMATCH`. Its own header explains the diagnosis: expected
identifiers were being re-derived at check time from things that move - a mutable envelope, a
seat's `current_run`, or "the latest run" - so a later write could change what a finished run
was expected to be. That is not a matching-rule problem, and it is not fixed by widening the
match.

### How the expectation is captured and frozen

`captureRunSnapshot(spec)` is called once, immediately before dispatch, and returns a deeply
frozen snapshot of exactly what this run expects:

| Snapshot field | Value |
| --- | --- |
| `run_id` | `envelope.run_id`. |
| `thread_id`, `turn_id` | `spec.threadId`, `spec.turnId`, or `null`. |
| `source_hash` | `hashSourceSet` over the bound files, or `null` when nothing is bound. |
| `seat_id`, `task_id`, `project_id`, `workspace_id` | Copied from the envelope. |
| `source` | `spec.source`, or `dispatch_transport_ids` when a thread id was supplied, or `mutable_envelope` when neither was - provenance, so a trace can say where the expectation came from. |
| `captured_at` | Timestamp of capture. |
| `transport_ids_confirmed` | `false` at capture. |

`deepFreeze` walks every nested object and calls `Object.freeze`, so under strict mode an
accidental write throws instead of silently changing history.

The transport's thread and turn ids are only known *after* dispatch returns, and they are
recorded as a separate frozen pair by `captureTransportIds(threadId, turnId, at)`
(`source: 'transport_dispatch_response'`) rather than written back into the run snapshot.
Writing back would reintroduce exactly the mutation the design removes. `effectiveExpectation`
then builds a **new** frozen comparison view from the run snapshot plus those ids, taking the
thread and turn id from the transport when present and appending `+transport_dispatch_response`
to the `source` string. The run snapshot itself is never modified, so the expectation recorded
at dispatch stays auditable even if a transport later disagrees with itself.

### Why re-deriving the expectation is a defect

If the expected run id is read from a mutable envelope at check time, then anything that
rewrites that envelope changes what a past run is expected to be. The code carries the
measured consequences of that class of bug in `workbench/seats/seat.js`: an earlier version
set `envelope.run_id` during `bindRun`, which replaced the id the prompt had told the model to
echo, and the next turn failed validation three layers away with "run_id must be a non-empty
string". The current `bindRun` records the run on the seat and leaves the caller's envelope
alone.

### What the trace records

`correlateWithSnapshot` returns a `trace` object with the expected value, the received value
and where the expected value came from:

- `expected_run_id`, `received_run_id_ack`
- `expected_thread_id`, `received_thread_id`
- `expected_turn_id`, `received_turn_id`
- `expected_source_hash`, `received_source_hash_ack`
- `expected_source`

The trace never contains credentials, tokens, or the packet body - only identifiers and
hashes - so it is safe to store and to paste into an issue. A mismatch is therefore
attributable to a named field instead of being a bare "not correlated".

Two honest notes about where this is wired up today:

- `workbench/protocol/runs.js` calls `checkCorrelation` with `expectedSourceHash` only, so its
  run id expectation comes from `envelope.run_id`; that path records a disposition but no
  trace.
- `workbench/scripts/autonomous-loop.js` is the caller that takes the full route:
  `correlation.captureRunSnapshot` at dispatch, then
  `protocol.correlateWithSnapshot(envelope, runSnapshot, reply)`, and it reads
  `corr.trace.received_run_id_ack`, `corr.trace.received_source_hash_ack` and
  `corr.trace.expected_source` into the evidence record.

## 6. TOCTOU

Time-of-check to time-of-use: the worker reasons about a file, time passes, the file changes,
and the review or approval is applied to a basis that no longer exists. A worker can take
minutes, and in that time a human can edit the file.

### Captured at dispatch

`captureSourceFiles(projectRoot, relPaths)` records, for each relative path:
`path` (with backslashes normalised to `/`), `sha256`, `bytes`, and `present_at_dispatch`.

A file that cannot be read is recorded with `sha256: null` rather than omitted. The comment
states why: an omitted file looks like "not part of the scope", whereas a null hash says "this
was in scope and could not be verified".

### Re-verified before review

`verifySourceUnchanged(projectRoot, sourceFiles)` returns
`{ok, status, changed, missing, verified, total}` and sets `status` to
`RUN_STATUS.SOURCE_CHANGED_SINCE_REVIEW` when anything is wrong:

- A file that is absent now and was absent at dispatch (`sha256` was `null`) counts as
  **verified**: consistent absence is not a change.
- A file that is absent now but had a hash counts as **missing**.
- A file whose current `sha256` differs is pushed to **changed** as
  `{path, at_dispatch, now}`.

Both `changed` and `missing` make the result not ok. That is how an absent file is recorded:
the run does not proceed and the path is named, rather than the check silently passing because
the file could not be hashed.

### The order, and what a mismatch means

`completeFromReply` in `workbench/protocol/runs.js` fixes the order: correlate first, then
re-hash, then allow review. On a TOCTOU failure the run status becomes
`SOURCE_CHANGED_SINCE_REVIEW` and the reply carries this note:

> No patch may be applied. Re-dispatch against the current source instead of reviewing a stale
> basis.

The run is stopped before any human is asked to approve anything, because an approval given on
a stale basis is worthless.

### The other direction

`workbench/transports/source-attachment.js` closes the same hole from the packet side. When a
transport declares that it cannot read files, the packet must carry the content, and
`buildSourceAttachment` refuses to embed a file whose live hash does not equal the envelope's
recorded hash - it records it under `[SOURCE NOT EMBEDDED]` with a `hash mismatch` reason
instead. Embedding content that disagrees with the bound hash would manufacture a
verification. It also declares truncation in the packet rather than silently cutting a large
file, at `MAX_EMBED_BYTES` = `120000`.

## 7. Independence

A second seat is not automatically an independent review. A reviewer that shares the worker's
provider is a second opinion from the same brain, and declaring that requirement satisfied
because a second seat existed would be the single most misleading thing the system could do.
So independence is a checked property, relative to the **worker's provider**.

`checkIndependence(envelope, workerSeat, reviewerSeat)` returns `{required, satisfied, detail}`,
plus `worker_provider` and `reviewer_provider` in the branches where both are known. It is
called from `recordReview` in `workbench/protocol/runs.js` and the result is stored as
`run.independence`.

| Outcome | Returned when |
| --- | --- |
| `required: false`, `satisfied: null` | `envelope.review_requirements.independent_provider` is not `true`. Detail: `independence was not required for this run`. |
| `required: true`, `satisfied: false` | Independence was required but no reviewer seat is recorded. Detail: `independence required but no reviewer seat is recorded`. |
| `required: true`, `satisfied: false` | Either provider is missing, so independence cannot be judged; the detail names both values. |
| `required: true`, `satisfied: false` | The worker's `provider` and the reviewer's `provider` are equal. Detail begins `INDEPENDENCE NOT SATISFIED:` and states that a second seat from the same provider is not an independent review. |
| `required: true`, `satisfied: true` | Both providers are known and differ. Detail: `worker <wp> vs reviewer <rp>`. |

Three things follow from this:

- The comparison is on `provider`, not on seat id, role or transport. Two seats of the same
  provider - even over two different transports - are not independent.
- `required` mirrors the envelope; it is not inferred from whether a reviewer happened to be
  available.
- `min_reviewers` is recorded on the envelope but is not read by this function.

In the evidence record the requirement is rendered from `rec.independence`: the markdown says
`Independent review: satisfied` only when `satisfied === true`, and otherwise prints the
`detail` verbatim, so a same-provider review is visible in the artifact rather than inferred
from a seat count.

## 8. The delivery state machine

### States

Every transport shares one vocabulary, defined as `DELIVERY` in
`workbench/protocol/transport-contract.js`. A transport may not invent its own state.

`IDLE`, `SUBMITTING`, `SEND_PENDING`, `USER_TURN_CONFIRMED`, `ASSISTANT_PENDING`,
`SEND_UNCERTAIN`, `COMPLETE`.

`TERMINAL` is `[COMPLETE, SEND_UNCERTAIN]`.

### Legal transitions

These are the edges in `LEGAL_TRANSITIONS`, written out one per line:

```
IDLE                 -> SUBMITTING
SUBMITTING           -> SEND_PENDING | USER_TURN_CONFIRMED | SEND_UNCERTAIN
SEND_PENDING         -> USER_TURN_CONFIRMED | SEND_UNCERTAIN
USER_TURN_CONFIRMED  -> ASSISTANT_PENDING | COMPLETE
ASSISTANT_PENDING    -> COMPLETE | SEND_UNCERTAIN
SEND_UNCERTAIN       -> (no outgoing edges)
COMPLETE             -> (no outgoing edges)
```

The same graph as a sketch. The edge list above is the verbatim data; this is a projection of
it.

```
   IDLE -> SUBMITTING -> SEND_PENDING -> USER_TURN_CONFIRMED -> ASSISTANT_PENDING -> COMPLETE
                                              |
                                              +----------------------------------> COMPLETE

   edges into COMPLETE         : from USER_TURN_CONFIRMED, from ASSISTANT_PENDING
   edges into SEND_UNCERTAIN   : from SUBMITTING, from SEND_PENDING, from ASSISTANT_PENDING

   SEND_UNCERTAIN : terminal, no outgoing edge
   COMPLETE       : terminal, no outgoing edge
```

`isLegalTransition(from, to)` answers the question directly, and `setDeliveryState` in
`workbench/seats/seat.js` is the only place a seat's state is written. An illegal transition is
refused with:

```
illegal delivery transition for seat <seat_id>: <from> -> <to>
```

along with the list of legal next states for the current one. How a transport reaches each
state is its own business: the synchronous HTTP transport still walks
`IDLE -> SUBMITTING -> USER_TURN_CONFIRMED -> COMPLETE` explicitly rather than skipping the
machine, so the states stay comparable across transports.

### `SEND_UNCERTAIN` is terminal, and no retry exists in code

`SEND_UNCERTAIN` has no outgoing transitions, and `mayRedispatch(deliveryState)` returns
`allowed: false` for **every** input, including the two terminal states. A blind retry is
therefore structurally impossible rather than merely discouraged: there is no state from which
the code will agree to send a second packet for the same run.

The three reasons it can give are distinct, and worth reading as the policy:

- From `COMPLETE`: `this run already completed; a new run should be dispatched instead`.
- From a terminal state: `the outcome is uncertain and the decision belongs to the user, not to
  an automatic retry`.
- From any other state: `a packet for this run is already <state>; re-dispatching would post a
  SECOND message into the same conversation. Only observation is permitted until the state
  settles.`

A duplicate message is unrecoverable; a delayed message is not. That asymmetry is the whole
argument for the shape of this machine.

A terminal state also files the run rather than dropping it. `setDeliveryState` writes the run
to `unresolved_run` on `SEND_UNCERTAIN` (it needs a human decision, not an audit trail) and to
`last_completed_run` on `COMPLETE`, then clears `current_run`. The id is the most valuable fact
in an uncertain outcome, and discarding it would leave an operator unable to search the
conversation for that run's ack.

### What `settleTurn` does, and the proof it requires

The anti-duplicate rule is "one message in flight per seat", enforced by keeping `current_run`
set. But a transport can legitimately report `SEND_PENDING` - the send executed, the new turn
is not observable yet - while the reply has in fact arrived and been read. The seat then holds
the run open and the next dispatch is refused, which is how a measured two-task goal stopped
at `BLOCKED` after one task. The guard was right; what was missing was a legal way to close a
turn that had demonstrably landed.

`settleTurn(seat, evidence)` closes it, and it claims exactly one thing: the dispatched turn
landed, because a reply carrying **this** run's id was observed. It does not claim the reply is
correct - the supervisor decides that - and it cannot be used on `SEND_UNCERTAIN`, which has no
outgoing transitions. It moves `SEND_PENDING -> USER_TURN_CONFIRMED -> COMPLETE`, both legal
edges, so nothing here invents a shortcut.

The proof is required, not optional:

- From `USER_TURN_CONFIRMED`, `ASSISTANT_PENDING` or `COMPLETE` it delegates to `completeTurn`,
  which closes those states.
- From `SEND_PENDING` it needs `evidence.replyText` as a string, and that string must contain
  the seat's current run id (`text.includes(runId)`). Without it the refusal is
  `refusing to settle a pending send: the supplied proof does not carry run id <id>`, with the
  hint that a pending send may only be closed by a reply that identifies this run, never by a
  timeout.
- With no current run id there is nothing to match the proof against, and it refuses.
- From any other state it refuses, and when the state is `SEND_UNCERTAIN` the hint says a human
  must confirm whether the message landed.

Without the proof requirement this would be a general-purpose "close a pending turn" call,
which is precisely the hole the anti-duplicate rule exists to plug. Note also what did **not**
happen to the machine: no transitions were added. The prohibition stands, and the new call
walks existing edges.

`completeTurn(seat, detail)` is the narrower sibling. It closes only
`USER_TURN_CONFIRMED`, `ASSISTANT_PENDING` and `COMPLETE`, files the run into
`last_completed_run`, clears `current_task` and `current_run`, and returns the seat to `IDLE`.
It refuses anything else with:

```
refusing to close a turn in state <state>: only a confirmed or completed turn may be closed
```

and the hint that a pending or uncertain turn must be observed or left alone, because closing
it would allow a duplicate send.

## 9. Walkthrough

One dispatched task, end to end, with the function names involved. The orchestrated version of
this sequence is `newOrchestrator(...)` in `workbench/protocol/runs.js` (`open`,
`observe`, `completeFromReply`, `recordReview`, `recordApproval`, `finalize`); the version that
exercises the frozen snapshot and the ack trace is `workbench/scripts/autonomous-loop.js`.

1. **Build the envelope.** `newRunId(scope)` produces the run id, then
   `buildEnvelope(spec)` captures the source hashes through `captureSourceFiles`, records the
   permissions and the review requirements, and returns `{ok: true, envelope}`. A missing
   required field returns `{ok: false, error}` here, before anything is sent.
2. **Validate the shape.** `validateEnvelope(envelope)` checks the required strings, the
   `source_files` entries, the four permission arrays and `review_requirements`.
3. **Freeze the expectation.** `captureRunSnapshot({envelope, source})` deeply freezes
   `run_id`, `source_hash` (via `hashSourceSet`) and the identifiers, and records where the
   expectation came from.
4. **Render the packet.** `render(envelope, opts)` calls `pickRenderer`, which selects
   `renderStructured` or `renderForHuman` from `RENDERERS`; both call `ackBlock`, and the
   `structured` dialect also emits `sourceBlock`, `permissionBlock` and `criteriaBlock`. When
   the seat's `capabilities.supplies_source_content` is `false` and a project root is supplied,
   `buildSourceAttachment` appends the verbatim source content.
5. **Dispatch.** `seat.dispatch(seat, envelope, opts)` enforces the guards in order: no run
   already in flight (`mayRedispatch`), the envelope belongs to this seat (`seat_id`,
   `project_id`, `workspace_id`), and `validateEnvelope`. It then calls `bindRun`, which
   records `current_run` and sets the delivery state to `SUBMITTING` without mutating the
   caller's envelope.
6. **The transport sends.** `transport.dispatch(envelope, packetText, opts)` posts one packet
   and returns a delivery *state*, never a reply. `setDeliveryState` records the transition and
   refuses it if it is not a legal edge.
7. **Observe, never resend.** `seat.observe(seat, envelope)` asks the transport what is known
   and updates the seat state. While a run is pending this is the only legal action.
8. **Read the reply.** `seat.read(seat, envelope, opts)` returns the reply text through the
   transport.
9. **Correlate.** `parseAck(replyText)` extracts `RUN_ID_ACK` and `SOURCE_HASH_ACK`, then
   either `checkCorrelation(envelope, replyText, {expectedRunId, expectedSourceHash})` or
   `correlateWithSnapshot(envelope, snapshot, replyText, {receivedThreadId, receivedTurnId})`
   compares them to the frozen expectation and returns `CORRELATED` or a quarantine
   disposition with a trace.
10. **Stop if it did not correlate.** An uncorrelated reply sets the run status to
    `STALE_OR_UNCORRELATED_REPLY` or `SOURCE_CHANGED_SINCE_REVIEW` and is never handed to
    review.
11. **Settle the turn.** `seat.settleTurn(seat, {replyText})` closes a turn that provably
    landed, so the seat can take its next run without the anti-duplicate guard deadlocking.
12. **Re-verify the source.** `verifySourceUnchanged(projectRoot, envelope.source_files)`
    re-hashes every bound file. `changed` or `missing` stops the run with
    `SOURCE_CHANGED_SINCE_REVIEW` and no patch may be applied.
13. **Review.** `recordReview(runId, {reviewerSeatId, verdict, summary})` accepts a review only
    while the run is `AWAITING_REVIEW`, resolves the reviewer seat, and records
    `checkIndependence(envelope, workerSeat, reviewerSeat)` alongside the verdict.
14. **Approve.** `recordApproval(runId, {decision, by, reason})` records the human decision as
    data. Applying a change is a separate, later step.
15. **Record.** `finalize(runId)` builds the Evidence Record with `evidence.buildRecord`,
    writes it with `evidence.saveRecord`, writes the markdown view next to the JSON, and
    returns `record_id` and `missing_evidence`. The record carries the ack values, the
    correlation disposition, the independence detail and the run status, so the whole chain
    from dispatch to record is auditable after the fact.
